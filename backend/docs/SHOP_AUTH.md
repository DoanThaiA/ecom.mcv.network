# Shop Authentication

This document explains the shop authentication flows implemented in `src/auth` and the OAuth provider flows for Google and Facebook.

## Core shop auth architecture

The shop auth system is implemented under `src/auth`.
Key modules and services:

- `AuthModule` - wires up email, phone, social, token, session, and profile services.
- `EmailAuthService` - email/password login, registration, confirmation, and password reset.
- `PhoneAuthService` - phone registration via OTP, phone login, OTP verification, and phone password reset.
- `SocialAuthService` - social login for Google/Facebook.
- `TokenService` - JWT access + refresh token generation and refresh semantics.
- `SessionService` - keeps session records and hash values used for token refresh invalidation.
- `AuthProfileController` - profile endpoints for refresh, logout, current user, update, delete, and social unlink.

## Shop auth flows

### Email auth

Endpoints:

- `POST /api/v1/auth/email/login`
- `POST /api/v1/auth/email/register`
- `POST /api/v1/auth/email/confirm`
- `POST /api/v1/auth/email/confirm/new`
- `POST /api/v1/auth/email/forgot/password`
- `POST /api/v1/auth/email/reset/password`

Behavior:

- `register` creates an inactive user and sends a confirmation email.
- `confirm` activates the user when the confirmation JWT hash is verified.
- `login` verifies email, password, active status, and returns tokens.
- `forgot/password` sends a password reset email with a JWT hash.
- `reset/password` verifies the hash, updates the password, and invalidates existing sessions.

Why this flow exists:

- Email/password is the primary shop credential model.
- Confirmation ensures valid addresses before activation.
- Password reset uses signed JWT hashes rather than a separate token store.

### Phone auth

Endpoints:

- `POST /api/v1/auth/phone/register`
- `POST /api/v1/auth/phone/login`
- `POST /api/v1/auth/phone/verify-otp`
- `POST /api/v1/auth/phone/forgot/password/request-otp`
- `POST /api/v1/auth/phone/forgot/password/verify-otp`
- `POST /api/v1/auth/phone/forgot/password/complete`
- `POST /api/v1/auth/phone/link/request-otp`
- `POST /api/v1/auth/phone/link/verify-otp`

Behavior:

- `register` creates an OTP record and sends it by SMS or ZNS.
- `verify-otp` uses the OTP to either create the new user or log in an existing phone user.
- `login` allows phone/password login when the user has a stored password.
- `forgot/password/request-otp` sends a password reset OTP.
- `forgot/password/verify-otp` validates OTP and returns a reset token.
- `forgot/password/complete` updates the password and deletes active sessions.
- `link/request-otp` and `link/verify-otp` can link a phone number to an authenticated user.

Why this flow exists:

- Phone-based auth supports mobile-first users and OTP registration.
- Rate limiting and daily OTP limits are enforced by `OtpService`.
- The flow separates OTP registration from password-based login.

### Token/session model

The shop auth system uses:

- `token` - JWT access token for API auth.
- `refreshToken` - JWT refresh token used by the refresh endpoint.
- `sessionId` and `session.hash` - stored in the refresh token payload, and validated during refresh.

Tokens are generated by `TokenService.getTokensData()`.

Refresh flow:

- `POST /api/v1/auth/refresh`
- Guard: `AuthGuard('jwt-refresh')`
- The request body is not required; the refresh token is sent via Authorization header.
- The refresh payload contains `sessionId` and `hash`.
- `TokenService.refreshToken()` verifies the session exists and hash matches, rotates the hash, and issues new tokens.

Logout flow:

- `POST /api/v1/auth/logout`
- Guard: `AuthGuard('jwt')`
- Deletes the active session record, which revokes refresh access.

Why this model exists:

- Storing a hash in session state allows refresh tokens to be invalidated by changing or deleting the session.
- Access tokens remain short-lived while refresh tokens can be rotated safely.

### Profile and account actions

Endpoints:

- `GET /api/v1/auth/me` - get current user
- `PATCH /api/v1/auth/me` - update current user
- `DELETE /api/v1/auth/me` - soft delete the current user
- `DELETE /api/v1/auth/me/social` - unlink a social account

Why this exists:

- Users can manage their own profile and authentication methods.
- Social unlinking is guarded to avoid removing the last available method.

## OAuth flows

Provider-specific endpoints exist for Google and Facebook.

### Google OAuth

Files:

- `src/auth-google/auth-google.controller.ts`
- `src/auth-google/auth-google.service.ts`

Endpoints:

- `GET /api/v1/auth/google/redirect` - returns the Google OAuth authorization URL.
- `POST /api/v1/auth/google/login` - accepts `{ code }`, exchanges it for Google profile data, and logs the user in.
- `POST /api/v1/auth/google/link` - links a Google account to the currently authenticated user.

Flow:

1. Frontend requests `/auth/google/redirect`.
2. Backend builds the Google auth URL with `client_id`, `redirect_uri`, `scope=openid email profile`, and a state token.
3. Frontend sends the user to Google.
4. Google returns an auth code to `${websiteDomain}/auth/google`.
5. Frontend sends the auth code to `POST /auth/google/login`.
6. Backend exchanges the code for tokens, verifies the ID token, reads the user profile, and calls `SocialAuthService.validateSocialLogin('google', socialData)`.

### Facebook OAuth

Files:

- `src/auth-facebook/auth-facebook.controller.ts`
- `src/auth-facebook/auth-facebook.service.ts`

Endpoints:

- `GET /api/v1/auth/facebook/redirect` - returns the Facebook OAuth authorization URL.
- `POST /api/v1/auth/facebook/login` - accepts `{ code }`, exchanges it for a token, and logs the user in.
- `POST /api/v1/auth/facebook/link` - links a Facebook account to the authenticated user.

Flow:

1. Frontend requests `/auth/facebook/redirect`.
2. Backend builds the Facebook auth URL with `client_id`, `redirect_uri`, `scope=email,public_profile`, and a state token.
3. Frontend sends the user to Facebook.
4. Facebook returns an auth code to `${websiteDomain}/auth/facebook`.
5. Frontend sends the auth code to `POST /auth/facebook/login`.
6. Backend exchanges the code for an access token and fetches the profile from `/me`.
7. Backend calls `SocialAuthService.validateSocialLogin('facebook', socialData)`.

### Social login behavior

`SocialAuthService.validateSocialLogin()`:

- looks up an existing user by social ID and provider;
- if none exists, looks up by social email;
- if it finds a user by email, it attaches the social account to that user;
- if no user exists, it creates a new user with `provider` set to the social provider;
- it always updates avatar/email if changed and upserts the social account object.

This means social login is both:

- a login flow for returning users, and
- a user creation flow for new shoppers.

### Supported provider implementations

- Google: implemented in `src/auth-google`.
- Facebook: implemented in `src/auth-facebook`.

## Why shop auth is structured this way

- Email and phone auth cover standard consumer login methods.
- Social OAuth is delegated to provider-specific services for Google/Facebook.
- A shared token/session model keeps refresh handling consistent.
- `AuthService` is a facade; most business logic lives in specialized services.
- The auth flow keeps shop auth separate from CMS auth and user management.
